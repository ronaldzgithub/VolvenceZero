- 用户是谁

- 为什么这套技术能把转化率/留存/ARPU/支付频次提上去

8. 为什么一定要和蚂蚁合作，而不是和别的平台合作？

今天大多数 AI 系统的核心问题有三个。

第一，它们对用户的理解大多是静态的。  
模型一旦训练完成，对现实的理解就基本停在了某个时间点。它可以调用上下文、调用记忆、调用工具，但很难在真实交互中，持续修正自己的认知结构。

第二，它们缺少真正的长期闭环。  
从感知、判断、行动，到结果反馈、再到后续修正，这条完整链路，今天仍然更多依赖人或者外层 workflow 在兜底。也就是说，系统会响应，但不一定会成长。

第三，它们在关系型、高信任、高连续性场景里不够稳定。  
无论是情感陪伴、长期顾问、复杂咨询，还是多轮服务型交互，用户真正需要的不是“这一句答得不错”，而是“这个系统能不能持续理解我、记住我们之间发生了什么、并且在边界内变得更合适”。

Volvence 就是围绕这三个问题搭建的。

我们的核心思路不是把 prompt 做得更复杂，也不是让底层模型频繁重训。  
我们采用的是一套有界的持续适应架构：冻结稳定基底，把在线学习放在更高层的控制器、记忆、反思和策略更新上，让系统在真实交互中逐步形成对用户、关系、任务和环境的更好理解。

这里面有几个关键能力。

第一是 prediction error，也就是“预测和实际结果之间的偏差”，作为系统的原始学习信号。  
系统不是简单记录用户说了什么，而是会形成对结果的预期，再根据真实反馈去修正后续行为。这样它的学习不是靠人工打标签，而是靠交互结果本身不断驱动。

第二是多时间尺度学习。  
短期交互里的即时调整、一次会话里的阶段性变化、会话之后的慢反思沉淀、以及更重的离线更新，不走同一条路径。这样既能适应用户，又不会把系统变成不可控的黑箱。

第三是连续记忆，而不是简单的“有或没有 memory”。  
我们不是只做上下文拼接，也不是只做一个长期记忆库，而是让瞬时状态、会话状态、持久语义记忆和衍生索引各自有边界、有 owner、有更新规则。这使得系统能记住真正重要的东西，同时保持可审计和可删除。

第四是关系和任务双轨学习。  
很多系统把所有目标都压缩成“把问题答对”。但在真实产品里，任务结果和关系结果并不一样。用户有没有被听见、信任有没有被破坏、关系是否需要修复，这些都需要单独建模。我们把 world/task 和 self/relationship 分开追踪，这是我们和一般应用层 agent 的一个本质差别。

第五是安全边界和回滚能力。  
我们并不相信“让系统自由长大”是可落地方案。Volvence 从设计上就是 bounded 的：有 owner、有 contract、有快照、有审计面、有 staged rollout、有 rollback。这意味着它不是研究性质的无限自我修改，而是可以被产品化和治理的持续适应系统。

从产品角度讲，这套能力最适合的，不是一次性问答，而是长期、高频、需要关系连续性的场景。  
你们在材料里其实已经把这个方向定义得很清楚，包括几个已经落地的 vertical：

关系陪伴、工程结对、虚构角色、真实人物数字化身，以及私域长程顾问。

这些 vertical 看起来不一样，但底层共性非常强：  
都要求系统跨会话记忆、持续适应、形成长期 interaction policy，同时又不能失控。

所以我们不把自己看成某一个垂类应用团队。  
我们更像是在构建一层下一代 agent runtime，先从最苛刻的长期关系场景切入，再把能力沉淀成底层系统。

这也是为什么我们觉得和蚂蚁存在天然协同。

我们理解，蚂蚁不会只看一个 AI 产品能不能做 demo，而会看它能不能进入真实业务闭环、形成长期生态价值。

Volvence 和蚂蚁的协同，至少有三层。

第一层，是长期服务型场景。  
无论是支付宝里的用户服务、商家经营、生活服务、健康、教育、金融陪伴，还是更广义的私域顾问，这些场景都不是一次触达能解决的，而是要跨多次交互、跨多轮关系去优化结果。Volvence 的设计，就是为这种长期 interaction 而生。

第二层，是 agent 基础设施。  
当行业从 chatbot 进入 agent 时代，真正的挑战不再只是调用模型，而是如何让 agent 在长期交互中既会学习、又不失控。我们在做的其实是这一层 runtime 和 learning loop，而不仅是前端产品体验。

第三层，是可治理的个性化。  
蚂蚁非常重视大规模服务能力，也非常重视合规、边界和可控。Volvence 的架构不是“黑盒个性化”，而是有 typed outcome、显式反馈入口、可审计 memory、可回滚 adaptive layer 的个性化系统。这让它更适合进入高信任、大规模的真实服务网络。

如果从合作路径上说，我们不建议一开始讲得太大。  
更现实的做法，是先找一个高价值、强连续性的场景，做小范围验证。

或者一个高频但高信任门槛的服务流程场景。

在这种场景里，我们最先验证的不是“模型更聪明”，而是三个结果：

第一，用户是否愿意持续回来。  
第二，系统是否会随着真实反馈逐步变得更合适。  
第三，这种适应是否是可审计、可控、可复制的。

如果这三个结果成立，那么它的价值就不仅是提升一次回答质量，而是提升整条长期服务链路的效率和体验。

今天很多团队在讲 agent，但多数 agent 仍然停留在“任务执行器”层面。  
我们关注的是另一个更难、但也更稀缺的能力：让系统在长期关系中，持续学习，持续修正，持续变得更适配，同时保持边界和治理能力。

如果这个能力成立，它不只是一个陪伴产品的优化项，
