## 1. 用户

_2026-07-23T13:54:17.317Z_

正是因为推荐系统是工业界唯一经历过“超大规模、超高并发、真在线学习”洗礼的领域。而大模型（LLM）目前的训练范式，本质上是“炼金术”式的离线静态锻造。

把推荐系统的经验移植到LLM持续学习上，绝不是牵强附会，而是工程范式的降维打击。具体来说，推荐算法在以下四个维度上，天然就是“在线学习”的完美试验场：

1. 数据流的本质：非平稳流（Non-stationary Stream） vs. 静态快照
推荐系统：每天有上亿用户产生新行为，每分钟都有新内容（新闻/视频/商品）上线。数据分布不是固定的，而是随着社会热点、季节、用户年龄实时漂移。如果不做在线学习，推荐模型三天内就会“过时失效”。

对应LLM痛点：世界知识每分每秒都在变（比如今天某公司股价暴跌、某地突发政策）。静态LLM的知识截止到训练集日期，永远滞后。推荐系统的在线学习架构，天然就是为处理“分布漂移（Distribution Shift）”而生的，而这正是持续学习要解决的核心数学问题。

2. 反馈信号的密度与延迟：毫秒级密集奖赏 vs. 稀疏延迟奖赏
推荐系统：用户是否点击（CTR）、是否划走（停留时长）、是否下单（CVR）。这些反馈是“即时、密集、低成本”的。模型每毫秒都能拿到一个明确的标量奖励（Reward），非常适合做Online SGD（随机梯度下降）或FTRL（Follow The Regularized Leader）等在线优化算法。

对应LLM痛点：大模型生成一段文案，用户点不点赞、有没有解决商业问题，反馈极其稀疏且延迟（可能几天后才成交）。推荐系统虽然反馈密集，但它磨练出了“如何处理高噪声、稀疏ID特征”的工程能力。你们BP里提到的“主动学习找有价值反馈”，本质就是把LLM的稀疏反馈，用推荐系统的“多臂老虎机（Bandit）”策略去密集化采样。

3. 参数更新的“稀疏性”与“解耦”工程（核心机密）
推荐系统（尤其是字节的广告/推荐模型）：模型极大（千亿参数），但每次推理和更新并不动全量参数。它们依靠庞大的Embedding层（嵌入层），在线学习时，只更新被当前请求“命中”的那极少部分ID特征的嵌入向量，而底层的DNN（深度神经网络）全连接层更新频率极低或冻结。这种“冻结基底、只动轻量适配器”的范式，在推荐系统里已经玩得炉火纯青。

对应LLM的残差流（Residual Steering）：你在BP第4页提出的“14B基底冻结 + 500M参数学习可迁移规律”，这和推荐系统的在线更新范式完全同构！ 马志刚在字节时，绝对处理过“如何在大参数基底不动的情况下，用侧边网络（Side-network）实时吸收用户即时兴趣”的工程难题。他知道怎么避免“在线更新导致模型表征崩溃（Representation Collapse）”，这正是你们“更新门（Update Gate）”最需要的底层工程保障。

4. 灾难性遗忘（Catastrophic Forgetting）在推荐里是“可控特征”而非“缺陷”
推荐系统：用户的兴趣是“有生命周期的”（今天爱看萌宠，下个月爱看汽车）。系统需要主动“遗忘”过时的旧兴趣，快速“记忆”新兴趣。推荐系统中的在线学习，研究的就是如何在“有限显存”和“实时带宽”下，既保留长期共性（慢记忆），又覆盖短时爆发（快记忆）。

对应Volence的记忆分层：你们把记忆分为快/中/慢/极慢，这在纯LLM学术界是超前设想，但在推荐系统的召回与排序模块中，早就用“实时序列（Real-time Sequence）+ 长期用户画像（Long-term Profile）”实现了。马志刚带来的不是理论，而是这四层记忆如何在GPU集群上做数据流水线并行、如何做内存Swap、如何做容灾回滚的工业级源码级经验。

## 3. Codex（最终答复）

_2026-07-23T13:56:59.831Z_

结论：大方向有价值，核心类比成立，但目前这段话大约是“六成正确、四成过度包装”。适合内部阐述战略直觉，不宜原样放进 BP 或对投资人背诵。最大问题不是方向错，而是把“可迁移的工程经验”说成了“已经证明的技术同构”，并夹杂多个无法证实的绝对化判断。

逐点看：

1. 非平稳数据流：基本正确

推荐、广告、搜索确实长期面对概念漂移、新用户、新内容、热点突发和反馈闭环。字节公开的 Monolith 就明确把非平稳分布、稀疏动态特征、实时训练和容错作为核心问题。[Monolith 论文](https://arxiv.org/abs/2209.07663)

这套经验对 LLM 持续学习很有借鉴价值，但不能直接等同：

- 推荐系统主要学习“用户—内容—目标”的条件分布。
- LLM 持续学习还涉及事实一致性、语言能力、推理能力、安全边界和跨任务迁移。
- 对实时事实，RAG、工具调用和知识库通常比在线改权重更安全、更可追溯。
- “不在线学习三天就失效”没有普遍依据，应删除。

更准确的说法是：推荐系统是工业界处理非平稳反馈流最成熟的领域之一，而不是唯一领域。搜索、广告、风控、量化交易和机器人也长期处理在线分布漂移。

2. 反馈信号：方向对，但描述过度理想化

推荐系统的曝光、点击、停留和转化确实比 LLM 的长期任务成效更密集，也适合 contextual bandit、在线优化和反事实评估。

但以下表述不准确：

- “每毫秒都有明确标量奖励”不对。点击和停留只是带偏差的代理信号，不等于真实用户价值。
- 推荐反馈同样存在延迟、选择偏差、位置偏差、曝光偏差和策略诱导的数据闭环。
- CVR、留存、复访等信号可能延迟数天甚至数月。Google 的工业研究也专门讨论了长期目标稀疏、低信噪比，需要用短期行为做代理信号。[Google：长期用户体验代理信号](https://research.google/pubs/surrogate-for-long-term-user-experience-in-recommender-systems/)
- 主动学习不等于 bandit。主动学习决定“向谁索取什么标签”；bandit 决定“采取什么行动并在探索与利用间权衡”。两者可以组合，但不是同一个概念。

因此，更好的迁移点是：推荐系统擅长把多源、带偏、延迟反馈转化为可校准的训练信号，并建立探索、归因、去偏和在线实验闭环。

3. 稀疏更新与冻结基底：是最有价值的类比，但并非完全同构

推荐系统的超大 embedding table、参数服务器、稀疏读写、增量同步、过期淘汰和容灾机制，确实很值得迁移。Monolith 公开展示了 collisionless embedding、频率过滤、embedding 过期以及在线训练和 serving 同步等能力。[Monolith 开源说明](https://github.com/bytedance/monolith)

但“推荐 embedding 稀疏更新”与“500M 侧网络控制 14B LLM”不能称为完全同构：

- 推荐 embedding 通常由离散 ID 直接寻址，更新天然稀疏。
- LLM adapter、LoRA 或侧网络多数参与每个 token 的稠密计算与反向传播。
- 推荐目标通常是少数可观测指标；LLM 输出空间开放，能力间耦合更强。
- 即使冻结 14B，更新 500M 参数也不算典型的“极轻量在线更新”。优化器状态、激活、版本发布和并发一致性仍然昂贵。
- 冻结基底只能降低遗忘风险，不能自动解决侧网络漂移、路由坍塌、表示干扰或奖励投机。

所以，这里应该说“系统设计原则高度相似”，而不是“完全同构”。真正可迁移的是：

- 快慢参数分层；
- 稀疏激活与条件路由；
- 流批一体的数据管线；
- 更新门、限幅和异常熔断；
- shadow evaluation、灰度发布、版本回滚；
- 延迟反馈归因；
- 特征和状态的生命周期管理。

4. “灾难性遗忘是可控特征”：表达容易误导

推荐系统确实需要淡化过时兴趣，但“主动遗忘用户短期兴趣”和“神经网络灾难性遗忘”不是同一件事：

- 前者是目标层面的时间衰减和状态更新；
- 后者是学习新分布时，旧能力因参数干扰而非预期退化。

推荐系统本身也会遭遇增量训练过拟合、模型漂移和长期知识丢失。在线推荐研究明确指出，只用滑动窗口新数据会丢弃长期信息，并需要 prior 或稳定性约束。[在线推荐增量更新研究](https://arxiv.org/abs/2312.15903)

因此，应改成：

> 推荐系统把“该忘什么、以什么时间尺度忘、如何保留长期稳定偏好”做成了显式工程机制；这对设计 LLM 的快慢记忆和受控可塑性很有启发。但它不能直接解决 LLM 的灾难性遗忘。

5. 四层记忆类比：合理，但不要声称“早已实现同一件事”

“实时序列 + 长期画像 + 周期训练 + 低频重建”确实可类比为多时间尺度状态系统。但推荐中的用户画像主要服务排序，Volvence 的记忆还需要：

- 事件来源和证据；
- world/self 语义隔离；
- 关系连续性；
- 冲突消解；
- 信用分配；
- 可撤销与边界同意；
- 对策略和长期能力的影响。

所以推荐经验可以解决“基础设施和生命周期管理”的一大部分，却不能代替记忆语义、学习目标与治理机制。

最需要删改的几句话

以下表述风险较高：

- “工业界唯一”——改为“最成熟的工业领域之一”。
- “三天内过时失效”——无通用证据。
- “每毫秒明确奖励”——反馈是有偏代理信号。
- “完全同构”——只能说架构原则相似。
- “马志刚绝对处理过……”——除非有公开履历或本人确认，否则不能这样说。
- “不像 OpenAI 那样暴力回放数据”——缺乏公开证据，也制造了不必要的竞争性事实风险。
- “我们用在线贝叶斯增量更新”——只有已经实现、跑过实验并有指标时才能说。推荐领域确有已部署的序贯贝叶斯增量方案，例如 LinkedIn 的工作，但这不能自动成为你们的技术事实。[LinkedIn 增量学习论文](https://arxiv.org/abs/2108.13299)
- “不会 OOM 的 Shell 脚本和 CUDA Kernel”——工程师会觉得夸张；OOM、安全更新和回滚不是靠个人背景自动解决的。

建议对投资人这样讲

> 推荐系统不是我们要复制的产品形态，而是持续学习最重要的工程参照系之一。它已经在非平稳数据流、延迟与有偏反馈、超大规模稀疏状态、在线实验以及模型回滚方面积累了成熟经验。  
>   
> Volvence 借鉴的是这套快慢分层和受控更新范式：14B 基底保持稳定，较小的控制与适配层吸收新经验；任何在线变化都受到更新门、预算、影子评估和回滚机制约束。  
>   
> 但推荐系统经验不能直接解决 LLM 的开放式生成、长期信用分配和灾难性遗忘。因此，我们把它作为工程骨架，而不是把推荐算法简单移植到 LLM。团队成员的推荐系统经历，价值在于把在线学习从算法原型变成可监控、可灰度、可回滚的生产系统。

一句话评价：这段话抓住了一个很强的战略洞察——“推荐系统人才对持续学习基础设施非常相关”；但它尚不能证明“推荐在线学习等于 LLM 持续学习”，更不能仅凭履历证明 500M 侧网络已经能安全撬动 14B 基底。对外应把“必然成功”降为“高度相关的工程能力 + 仍需验证的技术假设”。

设计上的优点是主题明确、人物形象醒目、学术背书完整。主要问题是右侧文字偏多、字号与行距较紧，底部团队信息拥挤；人物剪影和装饰元素占比较大，压缩了有效内容空间。此外，正文大量居中排版不利于阅读长句。

如果用于正式 BP，建议把右侧压缩成三项核心证明：

1. CMU 机器学习博士与研究方向；
2. 主动学习可降低标注成本、迁移学习可提升泛化；
3. 20 年研究积累、30+ 顶会顶刊成果。

底部团队成员可以改为三张简洁人物卡片，正文改为左对齐，并用一组量化指标替代重复描述，页面会更专业、易读。
