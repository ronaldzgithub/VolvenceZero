_2026-07-28T18:55:40.251Z_

可以并行测，但不能并行“晋升”。

我会这么切：

**可以并行的：**
- 不同 debt 的 `Stage 0` / SHADOW / report-only 证据，比如 #85 relational soft verifier、#88 learned temporal backend、#89 CMS torch、#90 active learning 这类探针，原则上可以并行跑。
- evidence pipeline 里的独立采集项也可以拆开跑：`real-soak`、`capacity-ladder`、`same-substrate-ablation` 在资源允许时可并行产 artifact。
- 脚本本身支持 `--only` / `--from-stage`，说明它不是只能从头顺序跑。见 [scripts/run_learned_active_evidence.py](/Users/mengfu/Documents/GitHub/volvence/scripts/run_learned_active_evidence.py:27)。

**必须顺序走的：**
- learned backend 的 ACTIVE 晋升必须按：
  `runtime → SSL → Internal RL → CMS torch`
  
  这个在 [docs/current.md](/Users/mengfu/Documents/GitHub/volvence/docs/current.md:339) 明确写了，原因是 SSL 依赖 runtime representation，Internal RL 依赖 runtime+SSL 稳定 latent space；一次 flip 多个组件会丢因果归因和回滚边界。
- `build-promotion-evidence` / `evaluate-promotion` 不能早于必需 artifact。比如 promotion 需要连续 real-soak、组件控制臂、CMS A/B、rollback、latency/safety gate 等。
- P1 只能给 directional / weak-positive，不能直接升级成 `first-stage-retained`；那个需要 P2 held-out multi-seed。

实际策略：**测试采集并行，结论合成串行，默认状态晋升串行。**  
并行跑时最好每条 lane 用独立 `--output-dir`，避免 `.runner/<stage>.json` marker 或 artifact 互相覆盖；GPU/端口型任务也要分资源，不然 Companion Bench 服务和 HF runtime 会互抢。

## 8. Codex（最终答复）

_2026-07-28T18:55:40.254Z_

可以写“终态代码”，但不能直接把系统当成“终态已成立”。

更准确地说：

可以：
- 一次性把 Stage 2 需要的接口、artifact shape、rollback drill、promotion gate、report 字段都先写好。
- 默认保持 `SHADOW` / `DISABLED` / opt-in，用测试证明“终态路径可被启动、证据不够时会 fail loudly”。
- 用 `--only` 跑某些终态 gate 的 dry-run / synthetic / fake-provider / artifact parser。
- 提前写好 `ACTIVE` 分支，但让它只能由 evidence artifact 通过 gate 后启用。

不可以：
- 直接把默认 wiring 改成 `ACTIVE`，然后用通过/失败来“探索”它是不是安全。
- 同时 flip runtime + SSL + Internal RL + CMS torch，再看整体分数，因为失败时不知道是谁的问题，成功时也没有因果归因。
- 用 P0/P1 的结果去声明 P2/first-stage retained。
- 绕过 Stage 0/1 的证据依赖，比如 #85 没有外部人审锚就不能验证自我确认，#88 没有 ≥500 real trace 就不能说 learned temporal backend 可晋升。

所以我建议的工程打法是：**实现可以向终态靠前，默认行为和晋升结论必须按 stage 走。**

一句话版本：  
**代码可以先写终态，测试可以并行采证，但 production/论文口径/默认 ACTIVE 必须逐级解锁。**  
这正好符合 R15：可解释、可回滚、有 evidence gate。
