## 四个技术问题

**一、`volvence` 臂不是 Volvence。** 脚本自陈 "bypasses propagate and is not the complete runtime stack"，是个 "bounded recurrent relationship-state prototype"。所以 pilot 实际比的是**一个新写的两层 MLP** vs **一个 256 token 的上下文窗口**。CMS、regime、owner、temporal——被研究的那个系统——一个都没参与。那个 0.0276 的优势跟 Volvence 架构无关。

**二、长上下文臂差了约 4000 倍。** context limit 256 token、平均截断 1456 token，对手是百万 token 上下文的现代模型。文档承认了，但这意味着 R1b 实质未完成。

**三、目标表示选错了。** 用的是冻结的 `all-MiniLM-L6-v2` 384 维。计划里写的是预测 **N+1 substrate 表示**。预测一个外部句向量编码器的输出，跟"系统自己的表示随相处变得更可预测"不是一回事——而后者才是命题。

**四、容量阶梯测的不是 ETA。** n_z 3→64 让 cosine 从 0.048 涨到 0.318，那是新 forward head 的容量，不是 temporal controller 的 `n_z`。文档自己也写了禁止据此改 temporal 默认值或删 `_step_impl_legacy`。所以 R3 没动。

分析纪律是：

1. 运行中只看进度、错误和 artifact 完整性。
2. 不提前查看效应后修改阈值、seed 或样本。
3. 全部完成后再跑独立审计和正式分析。
4. 中间材料只能用于故障诊断，不能当结论。
5. 七日实验的人类感知结论仍需要真人盲评；自动矩阵不能替代它。

两个 MPS 推理测试不能同时跑。它们会争抢统一内存，容易产生 OOM、延迟污染和不可比较的性能数据。新入口共享互斥锁，会阻止并发启动。

可以同时进行的只有：

- 一个实验占用 MPS；
- 另一个执行 `status`、文档整理或纯 CPU 独立审计。

另外，当前旧七日进程是在互斥锁落地前启动的，不受新锁保护。因此必须等原终端中的七日进程结束，再启动 N+1 `preflight/smoke`。最稳妥的顺序是：

```text

→ 七日 independent audit
→ 释放 MPS
→ N+1 preflight
→ N+1 smoke
→ 后续补齐 R3/R4/R5
→ N+1 formal
```
